# CPU 对比、提频与复查方法总结（2026-10-18）

本文把 10-17 至 10-18 两天的工作（六核 CoreMark 对比、单发射 rv_core 从约 77 MHz 提到 100 MHz、上板与 35 分钟稳定性测试）整理成一套与开发软件无关的方法。每个阶段都写明：要做什么、通过标准是什么、当时实际遇到了什么问题、怎么解决的。文中提到的 Vivado、PDS、Icarus、xsim 都只是实例，换成其他工具，步骤和判断标准不变。

最终结果供参照：ACX750（XC7A200T-2）上 100 MHz 时序收敛（WNS +0.026 ns），板上 CoreMark 306.46（3.065 CoreMark/MHz），LUT 5,016；35.7 分钟、160 次连续运行 CRC 全对。对应报告见 `reports/analysis/2026-10-18-core-comparison`、`reports/analysis/2026-10-18-100mhz-timing-cuts`、`reports/board/2026-10-18-acx750-100mhz`。

---

## 0. 总原则

1. **先冻结基线，再改动。** 改动前保存一份完整的源码快照，并记录每个文件的哈希。之后所有“是否等价”的判断都和这份快照比。
2. **每个改动都是默认关闭的参数。** 关闭时必须与基线逐周期一致；打开时才允许时序变化。这样随时可以回退，也能单独量出每一刀的收益和代价。
3. **分数拆成三项分别测：** 周期数（CoreMark/MHz，用仿真测）、频率（用布线后静态时序测，再上板确认）、面积（用实现后的资源报告测）。不要用一个总分去倒推原因。
4. **资料里的数字只作线索，不作结论。** 本次 Gemini 整理的参考资料中，每 MHz 分数普遍偏高 15%~60%，VeeR 的 LUT 数写了约 8K，实测约 35K。凡是要拿来做决策的数字，都在统一条件下自己测一遍。
5. **证据留全：** 输入哈希、完整命令、原始日志、解析后的结果文件；每次运行都用新的输出目录，不覆盖旧证据。
6. **不擅自动外部环境：** 虚拟机不自己开关，连不上就告诉用户、改用本机工具；上板只写 FPGA 易失配置，不写 Flash；需要下载外部软件前先征得同意。

## 1. 阶段一：搭建可信的测量平台

目标：所有被比较的对象（不同的核、同一个核的不同配置）都在**同一份程序、同一个编译器、同一套编译选项、同样的存储时延**下测量，差异只能来自核本身。

### 1.1 统一条件
- 同一份上游 CoreMark 源码（不做修改），同一个编译器（GCC 15.2.0），同样的编译选项（`-O2 -march=rv32im_zicsr_zifencei -mabi=ilp32`，不用压缩指令）。
- 每个镜像都依次跑 performance（种子 0,0,0x66）和 validation（种子 0x3415,0x3415,0x66）两组，两组 CRC 都必须等于官方参考值，周期数才算数。
- 统一的平台：一块 128 KiB 双口 BRAM（取指口、数据口，都是一拍返回），外设区放 UART、64 位周期计数器和 LED。多数核能直接运行**完全相同的二进制**。

### 1.2 遇到的问题与解决

| 问题 | 现象 | 解决办法 |
|---|---|---|
| 各核总线协议不同 | OBI、SCR1 的原生存储接口、Taiga 的本地存储口加 Wishbone、VeeR 的 64 位 AHB-Lite、VexRiscv 的缓存总线 | 每个核写一个很薄的包装层，严格模仿它自带的紧耦合存储/TCM 的时序（比如 SCR1 按它自己 TCM 的“当拍应答、下一拍 RDY_OK”来写，窄写数据按宽度复制、读数据按地址低位右移），而不是凭理解自己发明时序 |
| CV32E40P 用 ASIC 锁存器做时钟门控 | 在 FPGA 上不可综合，也没必要 | 换成直通。只有 WFI 会关时钟，基准程序不执行 WFI，所以不影响结果 |
| VeeR 没有数据缓存，高分依赖内部 DCCM | 代码和数据不能放在同一块存储里 | 照它自己的 CoreMark 布局：代码放外部存储，经 I-cache 取指；只读数据、数据和栈放 DCCM，由启动代码从镜像中拷贝过去。数据区所在的 0xF 区不允许放别的设备，所以外设移到 0xD 区 |
| VeeR 输出乱字符（`M ff`） | 串口丢字 | VeeR 默认把所有区域当作“不可缓存、无副作用”，状态寄存器的读可以越过还没发出的串口写。照它自带的启动代码写 `mrac=0x59555555`：所有区域可缓存、外设区标成有副作用。这个设置同时让 I-cache 生效 |
| 写 VeeR 配置要跑 perl 脚本 | 本机没有单独装 perl | 用开发软件自带 Git 里的 perl；路径要用正斜杠，否则 shell 会把反斜杠吃掉，子工具找不到 |
| VexRiscv 要先用 SpinalHDL 生成 Verilog | 本机 Java 坏了、没有 sbt；GitHub 和官方 JDK 下载链接被断开 | 在用户同意后，在虚拟机的用户目录装便携 JDK（清华镜像）和 sbt 启动器（阿里云 Maven 镜像），并配置 sbt 的仓库镜像。用 scp 传文件，传完去掉 BOM 和 CRLF，而不是用 PowerShell 管道传脚本（会混入 BOM 和 `\r`） |
| 调用参数不认 | sbt 启动器不认 `-batch` | 改成 `< /dev/null` 方式非交互运行 |
| 资料数字与实测差异大 | 如 VexRiscv 资料写 3.45，实测 2.60 | 用官方 README 的数字（2.57）交叉核对；实测和官方对上了，说明包装和测量本身可信 |

### 1.3 仿真本身的问题（最容易浪费时间的一类）

| 问题 | 现象 | 根因 | 解决办法 |
|---|---|---|---|
| VexRiscv 仿真 CRC 错误 | 连 `-7×3` 都算成 3 | 不是乘法器坏了，而是 load 读回了旧值。追到 D-cache 发出 redo 时，分支跳转仲裁的有效位是 X，选错了目标 PC。X 来自**没有初值的 RAM**（分支预测历史表、寄存器堆、缓存的数据和标签），FPGA 上电时它们都是 0 | 测试台在 0 时刻把这些存储阵列清零，与 FPGA 上电状态一致；主存也先清零再加载固件 |
| 怀疑是仿真器的问题 | Icarus 结果不对 | 先换另一个仿真器（xsim）跑同一个测试：结果完全一样，说明问题真实存在、不是仿真器 bug | 换仿真器交叉验证，再用定向的访存小测试（字节/半字写读、超出缓存容量的写读、乘除）缩小范围 |
| Taiga 在 RTL 仿真里卡死 | 断言每拍刷屏；关掉断言后 40 分钟没有任何输出 | 同样是未初始化的 LUTRAM 带来 X，进入控制逻辑 | 改用**综合后的功能网表**仿真：综合后所有 RAM 初值都是 0，行为与 FPGA 一致。网表仿真慢，CoreMark 改跑 1 次迭代；先在另一个核上对照 1 次与 5 次迭代的每迭代周期（差 0.01%），证明可比 |
| Taiga 上游代码有 bug | Vivado DRC 报同一个信号被两个寄存器驱动 | 归档版本里把 `is_sret` 误写成了 `is_mret` | 本地副本只改这一行并加注释，报告里写明这是唯一的补丁 |
| 日志暴涨拖垮整机 | 6.7 GB 日志，仿真进程吃掉 19 GB 内存，连读一个小文件都超时 | 断言每拍打印 | 结束进程；仿真脚本加“日志超过 50 MB 自动终止”；不要用会整篇读取大文件的命令去看日志，只读开头几行 |
| 宏定义跨文件失效 | VeeR 编译报“未定义的宏” | 工程文件里每一行是一个独立的编译单元 | 把所有源文件写在同一行，成为一个编译单元 |
| 命令行过长 | Taiga 源文件太多 | Windows 命令行长度限制 | 改用工程文件传文件列表 |
| 仿真太慢 | 一次 CoreMark 要几十分钟 | 按真实 115200 波特率打印要耗掉上千万周期 | 仿真时把串口分频设成 16（测试台按同样参数解码）。CoreMark 计时区间不含打印，不影响结果 |
| 仿真进程 CPU 占用很低 | 怀疑被系统节流 | 实际只是慢，换启动方式也没变化 | 先量一小段已知周期数需要多少时间，估出总时长，再决定换工具还是减少迭代次数，不要在“看起来像节流”上花时间 |
| 输出被缓冲看不到进度 | 日志迟迟为空 | 重定向到文件时输出有缓冲 | 加周期性进度打印，用直接重定向而不是管道；或者先跑一小段确认速度 |

## 2. 阶段二：定位时序瓶颈

### 2.1 方法
1. **用偏紧的约束探频。** 直接把约束设在目标频率（这次是 100 MHz），用默认布局布线选项跑一遍，从 WNS 推算可达周期。目的只是摸底。
2. **把最差的 100~200 条路径按“起点 → 终点”归类**，统计每类的条数、最差余量、逻辑级数、布线占比。看结构，不只看最差的那一条。
3. **读懂路径经过了什么。** 打开最差路径逐级看网表名，对照 RTL，写出“一拍里串了什么”。这次是：BRAM 读出 → load 字节对齐 → 旁路到操作数 → 分支比较 → 组合重定向 → 前端 PC / 预测器 / 全流水线停顿信号（扇出 239）。另外还有一条经过单拍 33×33 乘法（4 片 DSP 级联）。

### 2.2 遇到的问题与解决

| 问题 | 解决办法 |
|---|---|
| 早先的报告说“单发射核只能到约 45 MHz” | 那是在 25 MHz 约束下由余量推算的：约束松的时候工具不会使劲优化，推算出的上限偏低。改在目标频率下重新探测，实际约 81 MHz。**推算上限要在接近目标的约束下做** |
| 以为关掉几项提前访存优化就能提频 | 实测四项全关仍只有约 80 MHz，最差路径只是换成了“BRAM 取指 → PC 重定向”。说明问题在结构上，要切路径，而不是关功能 |
| 单独把主存从 128 KiB 缩到 64 KiB 没有效果 | 看综合报告才发现：因为字节写使能，工具把 RAM 按深度切块（每块 4K×9），读出要过深度选择器，写使能要译码高位地址。缩小容量只减少了块数，结构没变。见 3.4 |

## 3. 阶段三：切路径（每一刀的问题、做法、代价）

先用 HPM 计数器和历史板测数据核算预算：从 3.10 守到 3.0 以上，周期最多只能增加 3.3%。历史上各项优化的周期收益：EX 级提前 load −11.4%、EX 级提前 store −4.1%、一拍乘法 −2.6%、BTB 只记录跳转的分支 −1.0%、换 GCC 15 约 −8%。前两项远超预算，不能简单关掉。

### 3.1 重定向寄存一拍（`REGISTERED_REDIRECT`，周期 +1.07%）
- **问题：** load 数据当拍决定分支方向，再当拍驱动重定向、取指队列、PC、预测器和整条流水线的停顿。
- **做法：**
  1. 分支、mret、fence 的重定向在指令离开 X 级的下一拍才生效；这一拍误进入 X 级的错误路径指令被清除：不发射、不发提前访存请求、不启动乘除、不发 fence。
  2. 只寄存重定向判定的“原料”（是否 taken、目标是否≠预测、pc+4 是否≠预测、目标地址、是否 mret/fence），下一拍再做一个很小的选择，让 load 数据止步于触发器。
  3. 预测器训练也晚一拍。
  4. 陷阱（异常、中断）仍然立即重定向。
- **需要论证的正确性点**（写在代码注释里）：
  - 重定向那一拍不可能同时发生陷阱：发起重定向的指令此时在 M 级，且没有异常，所以既不会产生访存错误，也不满足取中断的条件。
  - mret 跳转用的 mepc 不会在中间被改：mret 是串行指令，发射时更老的指令都已退休，所以这一拍不会有 CSR 写。
- **一个“零代价”的配套改动：** 乘除和 fence 的等待条件原来依赖完整的异常判断（其中含 load 数据决定的地址/目标未对齐）。但这两类指令只可能有取指错误这一种异常，所以等待条件只看取指错误，逻辑等价，`xfire` 从此不再依赖 load 数据。

### 3.2 乘法拆成部分积（`MUL_PARTIAL`，周期 0）
- **问题：** 启动拍就把 33×33 的完整乘积算出来并寄存，要穿过 4 片 DSP 的级联。
- **做法：** 启动拍只寄存 4 个独立的部分积（各用一片 DSP，互不级联），原本就有的结果拍再相加。乘法延迟不变。
- **遇到的问题：**
  - 最初拼接部分积时位宽写错，多了 30 位，读代码时发现并改正。
  - 同一个信号不能既有连续赋值又在过程块里赋值（哪怕那段代码因参数不会执行也不行），否则编译不过。把原来的乘积寄存器改名为 `product_full`，两种实现之间用参数选择。

### 3.3 诊断计数器移出关键路径（周期 0）
- **问题：** 第二轮探测时，“BRAM → 分支/误预测计数器”成了最差路径：64 位计数器的使能依赖 load 决定的条件。
- **做法：** 改用已经寄存的训练事件计数，晚一拍。这些计数器只用于诊断，晚一拍不影响任何功能。

### 3.4 RAM 拆成字节通道（`RAM_BYTE_LANES`，周期 0）
- **问题：** 字节写使能要求每块 BRAM 至少 9 位宽，工具因此把 RAM 按深度切块：读出过选择器，写使能要译码高位地址（来自加法器进位链的末端），扇出也大。
- **做法：** 把 RAM 写成 4 个独立的 8 位通道存储，每个通道只有一个写使能。工具就能把每块 BRAM 配成全深度的窄位片：读出不再有选择器，写使能也不再有地址译码。每个通道从各自的初始化文件加载（`<INIT_FILE>.b0~b3`），固件构建时一并生成。
- **遇到的问题：** 存储模块移进生成块后，层次名从 `ram` 变成了 `word_ram.ram`，有一个分析用的测试平台按旧名字直接加载 RAM。改前先全仓库搜索对旧层次名的引用，同步修改。
- **配套：** 在确认 CoreMark 镜像加数据加 8 KiB 栈只有约 37 KiB 之后，把主存定为 64 KiB（块数减半）。

### 3.5 已有开关在目标约束下重新评估（周期 0）
- 以前移植的 `PREDECODE_X`、`FLAT_X_MUX`、`LUT_REGFILE` 当初只在 25 MHz 约束下测过，结论是“只省面积，不提频”。在 100 MHz 约束下重测，WNS 从 −2.02 改善到 −0.73 ns，同时 LUT 减少约 1,000。**结论：时序收益要在目标约束下评估，松约束下的结论不能外推。**

### 3.6 每一步的效果（100 MHz 约束）

| 配置 | WNS | 周期代价 |
|---|---:|---:|
| 改动前（128 KiB） | −2.36 ns | — |
| 只缩成 64 KiB | −3.11 ns（快速流程有 0.1~0.3 ns 波动） | 0 |
| + 重定向寄存 + 乘法拆分 | −2.02 ns | +1.07% |
| + 三个已有开关 | −0.73 ns | 0 |
| + 字节通道 RAM、重定向原料寄存、计数器移出 | −0.85 ns（快速流程） | 0 |
| 同上，用最强实现选项确认 | **+0.026 ns** | — |

## 4. 阶段四：验证（每一刀都要过）

### 4.1 冻结基线
- **问题：** git 的最新提交远远落后于工作区，不能当作“改动前”的版本。
- **做法：** 在备份目录里按文件大小和时间戳找到候选副本，再逐个比对哈希：**没改过的文件哈希与工作区完全一致、改过的文件才不同**，以此证明它就是改动前的冻结版本。

### 4.2 核级回归
- 复用项目已有的定向用例：乘除、前端/分支预测、ALU 边界值和随机依赖链、提前 store、取指/访存错误、中断，以及独立的参考预期值（ALU、乘除结果）。
- 新写一个回归脚本，参考核是冻结基线，覆盖“新开关的所有组合 × 已有开关全关/全开 × 三种预测器模式 × 取指直通开/关”：
  - **新开关全关：** 整条逐周期轨迹必须与冻结核字节一致；
  - **新开关打开：** 时序允许不同，但退休序列、访存请求、陷阱、最终寄存器、内存、CSR 必须与参考核一致，且所有独立预期值通过。
- 测试平台里的运行时断言（事务归属、乘除归属、重定向后不得取指、不合格的提前请求等）同时生效，任何非法状态当场报错。
- 结果：286 个用例 × 9 种构建 = 2,574 次运行，全部通过；其中 572 次逐周期一致，1,716 次架构一致。**每次再改 RTL，都要重跑一遍。**
- **遇到的问题：** 原有的回归脚本要求所有配置都逐周期一致，而新开关本来就会改变时序，不能直接用。解决办法是分两类判定（见上）。比较时要挑**不含周期号的记录字段**（退休、访存、陷阱、最终状态），排除逐拍的流水线记录。

### 4.3 基准程序仿真
- 每个开关组合都跑 CoreMark：两组种子 CRC 全对，并记录周期数，确认代价和预期一致（例如重定向寄存 +1.07%，其余为 0）。
- **结构性改动之后，再跑一次默认配置**（不同 RAM 大小都要跑），确认周期数与改动前完全相同（1,611,119）。
- 另跑一次项目原有的 SoC 自检程序，作为 SoC 层面的补充检查。

### 4.4 外部依赖不可用时
- 当天虚拟机连不上（原有回归依赖其中的 Verilator）。按约定不去开关虚拟机，改用本机的 Icarus/xsim 完成全部验证，并在报告中写明。

## 5. 阶段五：实现与收敛

### 5.1 两种实现模式
- **探频：** 约束设在目标频率，用默认的布局布线选项，只用来读 WNS、归类路径，速度快。
- **收敛确认：** 用最强的选项（这次是 ExtraTimingOpt 布局 + AggressiveExplore 物理优化与布线），只在探频显示“差得不多”时才用。

### 5.2 遇到的问题与解决

| 问题 | 解决办法 |
|---|---|
| 一次实现跑了很久还在布线 | 先看日志进行到哪一步、中间时序是多少。这次 WNS 一直在 −20 ns 左右，说明设计本身有问题，再怎么跑也不会收敛，应该立即停掉 |
| 根因：VeeR 的存储被做成了分布式 RAM | 综合报告显示 3,116 个 LUT RAM 和约 1.47 万个多路选择器。原因是存储写成了“按位掩码的读-改-写”，工具无法匹配块 RAM 模板。查官方文档（UG901）里 NO_CHANGE 模式的块 RAM 写法，按 way 拆成单写使能的 RAM 重写，问题消失。**每次实现后都要检查：存储是否真的映射成了块 RAM，乘法是否用了 DSP** |
| 激进选项在不可能收敛的约束下白耗时间 | 文档（UG835）说明 AggressiveExplore 布线的运行时间“可能显著更长”。探频阶段只用默认选项 |
| `report_qor_suggestions` 导致实现中途退出 | 这个功能超出当前许可证（BASIC）范围，报错后整个脚本退出，没生成后续报告。从脚本中删除；已经布线完成的检查点另写一个脚本重新生成报告，不必重跑 |
| 脚本里的引号写错（Tcl 中 `{路径}.b$lane` 不合法） | 运行一开始就失败。改用双引号拼接；**新脚本先用很短的任务跑通，再投入长任务** |
| 第一版位流里的固件只有 5 次迭代 | 只能用来看时序，不满足 CoreMark ≥10 秒的规则。按 100 MHz 计算至少需要 3,071 次，取 4000 次重新出位流 |
| 换固件后担心时序会变 | 存储初值只是属性，不影响布局布线。重新生成后核对：WNS、WHS、资源与原来完全相同 |
| 多个实现同时跑时内存紧张 | 每个实现限制线程数；同时运行的大型实现不超过两个；出现内存不足就减少线程数后重试 |

## 6. 阶段六：上板

### 6.1 步骤和检查
1. 先确认连接：列出串口和 USB 设备，确认串口芯片和 JTAG 线缆都在。这次第一次上板时板子没插好，没有串口，及时停下来告诉用户，而不是继续尝试。
2. 只写 FPGA 易失配置，不写 Flash。核对 JTAG 线缆序列号、器件型号、IDCODE、DONE=1。
3. 先打开串口再编程（编程期间引脚悬空会读到 0 字节，要过滤掉），抓取完整输出。
4. 自动检查：两组种子 CRC、“Correct operation validated”、无 ERROR 行、每次运行 ≥10 秒、按周期数和频率换算的分数。
5. 重复跑两次，周期数应完全一致。
6. 报告中注明：频率是由时钟源换算的标称值，没有单独测量；分数按标称频率计算。

### 6.2 关于频率测量
- 片上逻辑分析仪（ILA）是用被测时钟本身采样的，**测不出绝对频率**，只能证明逻辑在这个时钟下正确运行。
- 需要独立证据时：用电脑计时对照（板上计 N 个周期，电脑记录对应的实际时间，精度约 10⁻⁴），或者把时钟分频后从引脚输出，用示波器或频率计实测。
- PLL/MMCM 的输出是晶振的精确倍数，频率误差只来自晶振本身（一般在 ±50 ppm 以内）；真正的风险是这个频率下逻辑会不会出错，要靠时序余量加稳定性测试来覆盖。

## 7. 阶段七：稳定性测试

### 7.1 步骤
1. 固件改成无限循环：每轮依次跑 performance 和 validation，并打印轮次号；基准程序本身不改。
2. 位流重新生成，确认时序与资源和上板版本完全相同。
3. 主机端逐次检查：CRC、validated、无 ERROR、时长 ≥10 秒、周期数与参照值的偏差；连续 90 秒没有完成一次运行就判定为卡死。**任何一次不合格立即停止并报告。**
4. 运行时长至少 30 分钟，本次跑了 35.7 分钟、80 轮、160 次。

### 7.2 遇到的问题与解决

| 问题 | 解决办法 |
|---|---|
| 周期数的参照值怎么定 | 第 1 轮分支预测器是冷启动，会差几十万分之一，所以用第 2 轮作参照。实测第 3 轮起每轮只差几到几十个周期，原因是每轮之间串口打印的忙等次数不同，计时开始时分支历史略有差异。阈值设为 10⁻⁴（约 13 万周期），实际最大偏差 70 周期 |
| **监控脚本漏检**：第 2 轮起只看到 validation，没看到 performance | 增量解析时，同一次扫描如果匹配到两条记录，读取位置是按“相对切片起点”累加的，跳过了下一段的开头。改成用绝对位置继续扫描；**修好后先用已有的原始日志按不同分块大小回放**，确认每一次运行都能识别，再从头重跑完整的 35 分钟。作废那次的证据也保留并在报告中说明 |
| 记录里多出一个“第 0 轮” | 重新编程完成前，板上上一个程序还在跑，串口已经打开，收到了它的残留输出。报告中单独说明并排除在统计之外 |
| 稳定性测试没覆盖的范围 | 写明：更长时间（数小时）、温度变化、多块板子之间的差异都还没测 |

## 8. 报告与证据

每份报告固定包含：
1. **结论先行：** 一句话写结果，并写明哪些是仿真、哪些是静态时序、哪些是板上实测。
2. **对照表：** 改动前后的周期数、CoreMark/MHz、频率、分数、LUT/FF/BRAM/DSP、CoreMark/LUT。
3. **改动清单：** 每个参数做了什么、放在哪个文件、周期代价多少。
4. **每一步的效果：** 逐步的 WNS 变化。
5. **验证结果：** 回归规模和判定方式、CoreMark CRC、默认配置复查。
6. **证据路径与哈希：** 位流、固件、原始日志、结果文件。
7. **未覆盖的范围和已知风险：** 例如“余量只有 26 ps”“频率未单独测量”“上游补丁一行”。
8. **复现命令。**

数字只用实测值；资料中的数字单独列为对照，并注明出处。

## 9. 换开发软件或换板子时

**可以原样沿用的：**
- 第 0、4、7、8 节（原则、验证、稳定性、报告），与工具和板卡无关。
- 阶段三的切路径手法。RTL 改动都是通用写法，不依赖厂商原语。

**需要重新做的：**
1. **时钟：** 用新器件的 PLL 重新配置（盘古 200Pro+ 板载 27 MHz 晶振），重写时钟约束。
2. **存储和乘法器映射：** 不同厂商的块 RAM 宽度、字节写支持、DSP 尺寸都不同。字节通道拆分的思路在任何器件上都有好处，但要看综合报告确认实际映射；乘法的部分积切分要按新器件的 DSP 尺寸调整。
3. **时序：** 重新做一遍“探频 → 归类 → 切路径 → 收敛确认”。另一家器件的瓶颈不一定相同，频率也不能直接照搬；紫光 -6 速度等级的器件通常比 Artix-7 -2 慢，很可能需要再切下一刀（下一刀的候选见 `reports/analysis/2026-10-18-100mhz-timing-cuts`）。
4. **实现与上板脚本：** 换成新工具链的对应命令，但“探频/收敛两种模式”“只写易失配置”“编程前打开串口”“自动判定”这些规则不变。
5. **许可证和功能限制：** 先查清新工具哪些报告和优化功能可用，避免脚本中途因为许可证报错退出。

## 10. 常见坑速查

| 现象 | 先怀疑 |
|---|---|
| 仿真结果离谱，但逻辑看起来没问题 | 未初始化的 RAM 带来的 X；换一个仿真器交叉验证；用综合后网表仿真 |
| 实现跑得极慢、WNS 很差 | 存储没映射成块 RAM（看综合报告）；激进选项用在了不可能收敛的约束上 |
| 关掉某个优化开关却没有提频 | 瓶颈只是换了一条路径，要从结构上切 |
| 缩小存储没有效果 | 存储被按深度切块（字节写使能导致），要拆成字节通道 |
| 诊断逻辑出现在关键路径上 | 计数器使能依赖数据，改成晚一拍计数 |
| 宏定义未定义 | 编译单元被拆开了 |
| 机器突然卡死 | 日志暴涨或内存耗尽；限制日志大小和并行任务数 |
| 板上串口乱码或丢字 | 外设区的访存属性（是否有副作用）没有设置 |
| 监控脚本“全部通过”但次数不对 | 先核对检查到的次数是否等于应有的次数；解析器要用真实日志回放验证 |
| 结果比参考资料差很多 | 先确认条件是否一致（编译选项、扩展指令、存储时延），再怀疑设计 |
